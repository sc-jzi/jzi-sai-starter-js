# Bootstrap a freshly created site so the shared components work in it

> Rules: `.skills/RULES.md` (R1–R24) is the one source and wins over anything below; this skill refers to rules by number.

A site made from a site template has the standard presentation scaffolding but none of the project-specific items that ProsperaFinancial-style sites carry. The shared definitions (templates, renderings, rendering parameters under the project layer, `renderingsRoot` in `docs/ai/config/project.yaml`) already exist and are REUSED. This skill creates only what lives INSIDE the new site. Use the Marketer MCP; how to do nested placeholders, datasources and variants is in `.skills/sitecore-reference/references/placeholders-and-variants.md` (earlier notes in `agent-api-limitations.md` are history, not rules).

## Rules
- Run `node harness/scripts/bootstrap-plan.mjs <customer>` first; it lists exactly what is needed (`bootstrap-plan.md/json`).
- Before every write: `node harness/scripts/guard-customer.mjs sitecore-path <customer> "<path>"`.
- Use ids from the manifest ONLY for shared things (templates, folder templates, renderings, rendering parameters). Site-level ids in the manifest (any other site's `/sitecore/content/...` paths, variant definition ids, example items) belong to another site: never use or write them.
- Record every id you create or find in `industry-verticals/<customer>/docs/ai/demos/<customer>/site-manifest.json`; all later phases read site-level ids from there.
- Do not claim a write worked until you re-read it (several fields are silent-writes; see `sitecore-marketer-mcp-reference.md`).

## Step 0 — Probe (read-only)
With `get_content_item_by_path`, list and record in `site-probe.json`: `/sitecore/content/<coll>/<site>` children; `Home`; `Data`; `Presentation/{Available Renderings, Headless Variants, Partial Designs, Page Designs, Styles}`; `Settings`. Also confirm the shared layer exists (`renderingsRoot`, `projectTemplatesRoot` from `docs/ai/config/project.yaml`). If the shared layer is missing in this environment or collection, STOP and tell the SE: the components are not registered there and that is a separate (new-component) job.
If the probe shows there is no `Home` page (some site templates, e.g. Empty, may not create one), create it: `create_page(name="Home", parentId=<site root id>, templateId=<the derived Page template of step 4, or the Home template the site template defines>)`, read it back, and continue (R4: only after two logged failed attempts is it BLOCKED; it is not a question for the SE after approval, R1).
The probe decides each step below: create only what is absent.

## Step 1 — Data root and datasource folders
All page-section datasource content of the demo lives under this site's `Data` root (`/sitecore/content/<collection>/<site>/Data/<component folder>`), never in page-local `<page>/Data` folders; only the Header/Footer partial designs keep their own `Data` child (step 5). Record each folder id in `site-manifest.json` → `dataFolders`.
If `Data` is missing, create it (use the folder template the probe shows other Data roots use; if none, use the template the plan's `folderTemplateId` implies or the Data folder template of the reference site, note the assumption in `manual-tasks.md`, and continue). For each component with a datasource in `bootstrap-plan.json`: create `Data/<datasourceFolderName>` with `create_content_item`, template = `folderTemplateId`. Skip existing. The rendering's datasource location query looks under `$site/Data` for that folder template, so the template and the folder name must match the plan exactly.

## Step 2 — Headless Variants
**Container name = the RENDERING ITEM name, exactly, spaces and capitals included** (`Four Column CTA`, `Heading CTA`, `Three Column CTA`, `Page Content`), NOT the React component name (`FourColumnCta`): Sitecore matches the container to the layout definition item by name, and a container with the PascalCase name never matches (an earlier demo run: Four Column CTA rendered "Content SDK component is missing React implementation"). Take it from `bootstrap-plan.json` → `headlessVariantContainer` (= the rendering's item name from the manifest); if absent, the last segment of `rendering.path`. FIRST list `Presentation/Headless Variants` (the template site already has containers for many renderings): reuse an existing container with that exact name, create only the missing ones, and never create a second container whose name differs only in spaces/case. A stray wrong-named container from an earlier run: leave it, add one line under `## Info` in `manual-tasks.md` (R4). After creating, list the folder again and confirm every `headlessVariantContainer` name in the plan is present.

For each component: ensure `Presentation/Headless Variants/<container>` exists (template **Headless Variants**), then one **Variant Definition** per variant needed (always `Default`, plus every non-Default variant the plan uses, `WithLogoImage` for `Header`, and the CLIENT variant `<site.variantName>` for EVERY component in `bootstrap-plan.json`, header-area ones included: `Eyebrow`, `Header`, `Navigation`, `Footer`; the `Eyebrow` container may not exist in a new site: create it, template **Headless Variants**), names exactly as the TSX exports (`.skills/sitecore-add-variants/SKILL.md`). Record the variant ids in `site-manifest.json` (they feed the variant checklist).

## Step 3 — Available Renderings
Open `Presentation/Available Renderings/Page Content` (or the probe's equivalent). Its field cannot always be read through MCP. If you can read it: write the existing value + the plan's ids (concatenate, never replace). If you cannot read it, do NOT write: save the pipe-separated list from `bootstrap-plan.md` to `available-renderings.txt`, add "paste this list after the existing value of Available Renderings/Page Content" to `manual-tasks.md`, and CONTINUE: try `add_component_on_page` anyway (the API usually does not enforce Available Renderings). Do not ask or wait.

## Step 4 — Derived page templates
Never point new pages at another site's templates directly. For each distinct page type in `demo-plan.yaml` (`page`, `article`, `landing`):
1. Base = the shared template from `industry-verticals/prospera/docs/ai/catalog/page-template-registry.yaml` (e.g. `/sitecore/templates/Project/Financial/Pages/Article Page`). Read-only.
2. Ensure the folder `/sitecore/templates/Project/<collection>/Pages` exists (Template Folder; create parents if absent; guard-check the path first).
3. Create the template there: `create_content_item` with the **Template** template (`{AB86861A-6030-46C5-B394-E8F99E8B87DB}`), name = the base template's name (`Article Page`, `Page`, ...). Set its **Base template** field (`__Base template`) to the base template id, then re-read to confirm. No own fields are needed; it inherits fields, standard values and insert options from the base.
4. Record `{pageType: derivedTemplateId}` in `site-manifest.json` → `pageTemplates`. `demo-build-pages` uses these ids, never the base ids.
If the write is refused, try the other route once (guard path check, parent folder, template id), record the response in `harness/reference/marketer-mcp-tools.md` (limits); only after two failed attempts fall back to the base template and write ONE `BLOCKED after 2 attempts: "<error>"` line. Derived templates under `/sitecore/templates/Project/<collection>` are allowed by the guard: a refusal by `guard-customer.mjs` there is a guard fault to report, never a reason to skip the templates.

## Step 5 — Header and footer partial designs, Page Designs
**Before anything is placed: the header kit (code, deterministic).** `node harness/scripts/header-styles.mjs --customer <customer> --url <prospect url>` (skip when `header-styles.json` already exists from intake; it measures the prospect's real eyebrow bar, logo bar and menu: colours, sizes, fonts, spacing), then `node harness/scripts/header-kit.mjs --customer <customer>`. It writes, in the customer's own app copy only, the client variant `<site.variantName>` of `Eyebrow` (hardcoded links, phone, search button, CTA button; keeps the `eyebrow-left` / `eyebrow-right` placeholders), `Header` (copy of `WithLogoImage`) and `Navigation` (TOP LEVEL ONLY), plus their styles. Check that the app still type-checks (`node harness/scripts/build-check.mjs <customer> --quick`, R17). If the measurement fails (script exit 3 / `null` blocks), carry on with the neutral defaults and add "measure the header by eye" to `manual-tasks.md`. The Variant Definitions with that same name come from step 2; `sitecore-create-demo-variants` later only checks and refines these.
The header and the footer are added only as partial designs. They are never placed on a page, and their rendering XML is never copied into a page's `__Final Renderings` or `__Renderings`. A page design that does not merge them is fixed by correcting the partial (template and layout) and the Page Design mapping. Copying the chrome onto the page is not a workaround.
A partial design is an item in `Presentation/Partial Designs` that carries components. A page design is an item in `Presentation/Page Designs` that lists those partials and is mapped to page templates. All are created by API; do not give up on them without trying.
1. **Learn the pattern (read-only)** from the site's own `Partial Designs` / `Page Designs` (the site template may already include some) or, if empty, from the reference site in `sitecore-manifest.yaml`: the template id of a page design, the field names (partial designs list, template mapping `Template To Design`), the header and footer placeholder paths (`get_components_on_page(pageId=<reference partial id>)`), and the encoding of the mapping value. Never write to the reference. The partial design template is not learned: it is fixed, below. The folder you create under is not a partial design.
2. Create `Header` and `Footer` with `create_content_item`, parent = this site's `Presentation/Partial Designs`, template `{FD2059FD-6043-4DFE-8C04-E2437CE87634}`. That id is the Partial Design template. `{C3CEB23C-D66D-4EF5-99E0-D45F60C02583}` is the Partial Designs folder; an item on it is a folder, holds no layout, and a page design cannot merge it. Re-read each item (`get_content_item_by_id`) and confirm its template id is `{FD2059FD-6043-4DFE-8C04-E2437CE87634}` before recording it in `partialDesigns` or placing any component on it. Any other template, including the folder template: do not use the item, create the partial again on `{FD2059FD-6043-4DFE-8C04-E2437CE87634}`. Then fill them. Rendering ids: the manifest, otherwise look the rendering up by name under `renderingsRoot`. Placeholder names come from the code (`industry-verticals/prospera/src/components/navigation/*.tsx`). Nested placeholders are DYNAMIC and are DERIVED, never hardcoded: follow `.skills/sitecore-reference/references/placeholders-and-variants.md` section 1 (key = `<host placeholder path>/<child name>-0-<host DynamicPlaceholderId>`, e.g. `/headless-header/eyebrow-left-0-1`; the numbers come from the host instance you just added and change per page/partial). Add the host, read back its `DynamicPlaceholderId`, build the key, check it with `get_allowed_comps_by_ph`, add the child, re-read and confirm the child sits under that exact key. Every set of renderings in this step ends with that read-back.
   **Header partial design** — exactly this composition, in this order. The eyebrow bar has NO Navigation component: its links, phone, search and CTA are hardcoded in the client Eyebrow variant (step 5b).

   **Header data source (local data of the partial) — do these in this order:**

   3. Under the Header partial design create `Data` (same template the reference partials' `Data` child uses; probe it), and under it an item named `Header` based on the template from 2. Set `LogoImage` to the `imageFieldXml` from 1 (verbatim). Re-read the item: `LogoImage` is non-empty.

   **Footer partial design:** `SiteFooter` (rendering name in the manifest; data source = a footer item you create under the partial's `Data`, fields filled from the measured footer). ## Step 5b — Main menu (top level only) and the eyebrow bar
The prospect's header has TWO link groups and they are built differently. `nav.json` has them apart (`items` = main menu, `eyebrow` = the small bar above it, `eyebrowExtras` = phone number / CTA button, which are not pages). The plan gives every page a `navGroup` (`main` | `eyebrow` | `none`).
1. **Eyebrow bar = hardcoded, not CMS driven.** Its links, phone, search button and CTA come from the client Eyebrow variant that `header-kit.mjs` generated from `nav.json` (links to a planned page point at that page, the others at the prospect's URL). There is no Navigation component and no navigation filter for the eyebrow (the filter approach did not work and a Navigation component cannot render the phone, search or CTA). `navGroup: eyebrow` pages still exist as pages; they just must not appear in the Main Navigation.
2. **Find the filters (derived, never hardcoded).** What matters is the `NavigationFilter` FIELD on every individual page item ("Check to hide in navigation filters": Breadcrumb / Footer / Main / Sidebar / Sitemap Navigation). Read the field's definition on the derived page template (find the field item under the template, e.g. `get_content_item_by_path`; its `Source` says where the options live) and record each option's item id in `site-manifest.json` → `navigationFilters` (`{ "Main Navigation": "{id}", ... }`). If the options folder of the NEW site is empty, that is NOT the end and not a manual task: the Source may point outside the site (use those ids), otherwise create the five option items there with `create_content_item` (names and template copied read-only from the reference site's equivalents), then use their ids. Never use another site's ids. (The write works: an earlier demo run showed Main Navigation ticked on the pages that got it.)
3. **Page rule (applied while pages are built, `demo-build-pages` step 3).** The field is a "hide in" list, the ids joined with `|`. The Main Navigation shows ONLY pages with `navGroup: main` that sit directly under Home. EVERY other page (eyebrow pages, dropdown children and anything deeper, story pages) gets `Main Navigation` ticked. Home is not a menu entry.
4. **The Navigation component picks its filter and depth.** Read the Navigation rendering's parameters template (`get_component(<Navigation rendering id>)` → its Parameters Template; the manifest has it) and list its fields. Set the field that holds the navigation filter (e.g. `NavigationFilter`) to the `Main Navigation` id, and, if there is a levels/depth field, set it to 1, with the layout-XML route of step 5 (`--param <Name>=<value>`). If a field does not exist, write that in `harness/reference/marketer-mcp-tools.md` → "Verified methods"; it is not a stop, because the client Navigation variant (header kit) renders only the top level anyway and the page-level `NavigationFilter` values stay.
5. **Verify the result, not the settings.** Render the first sub-page (`get_page_screenshot` or the preview HTML): the menu lists exactly the planned `navGroup: main` top-level labels (Login included when planned) and nothing else: no second-level children, no eyebrow labels. If it lists more, the Navigation has no filter/variant applied: re-check items 3-4 and step 5 item 4.

## Step 6 — Verify and hand on
Re-read every created item (`get_content_item_by_path`), compare with the plan, list gaps. Header and Footer must each report template `{FD2059FD-6043-4DFE-8C04-E2437CE87634}`; an item on `{C3CEB23C-D66D-4EF5-99E0-D45F60C02583}` is a folder and the step is not done. No page's layout field contains the header or footer renderings. Header check (from `get_components_on_page` on the partial AND the layout XML, not from memory): Eyebrow above Header; Eyebrow variant = the client variant; ThemeSwitcher and LanguageSwitcher stored under `/headless-header/eyebrow-left-0-<id>` / `eyebrow-right-0-<id>` of the Eyebrow's real `DynamicPlaceholderId` (and NOTHING else in the Eyebrow); Header variant = the client variant and datasource = the `Data/Header` item with `LogoImage` filled with a Content Hub public link; Navigation under `header-right-0-<id>` of the Header's real id with `s:ds` = Home, variant = the client variant and its filter/levels parameters set (or the absence recorded). Every one of these via a read-back of the XML, never from the success messages. Then render the first sub-page (`get_page_screenshot`) and check the logo, the eyebrow bar (links, phone, search, CTA), the switchers and the top-level-only navigation are visible. Write `site-manifest.json`: `{ siteRoot, dataRoot, dataFolders: {Component: id}, variants: {Component: {Variant: id}}, availableRenderingsItem, pageTemplates: {pageType: id}, partialDesigns: {Header: {id, templateId}, Footer: {id, templateId}}, pageDesigns: {Page, Article}, home }`. `templateId` is copied from the `get_content_item_by_id` READ-BACK of each partial, not from the create call: `run-gate.mjs` fails unless both are `{FD2059FD-6043-4DFE-8C04-E2437CE87634}` (and names the folder template `{C3CEB23C-...}` when that is what was created). Run the guard `check`. Then continue with content (Phase 3) and `demo-build-pages`.
If a step fails twice, try the next route in its ladder; stop only when everything after it truly depends on it (see `demo-from-transcript` "Continuous run") and then report what exists, what is missing and the one thing that unblocks it.
