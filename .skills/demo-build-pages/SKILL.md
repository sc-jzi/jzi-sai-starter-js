# Create and assemble ALL planned pages (replaces "Home only" Phase 6)

> Rules: `.skills/RULES.md` (R1–R24) is the one source and wins over anything below; this skill refers to rules by number.

Called by `demo-from-transcript` (Phase T5) after the NEW site is created and bootstrapped, and theme, images and content items exist. Input: the approved
`industry-verticals/<customer>/docs/ai/demos/<customer>/demo-plan.yaml` (`site.pages`) and `content-map.yaml`.
Use the Marketer MCP tools. How-to for nested placeholders, datasources and variants: `.skills/sitecore-reference/references/placeholders-and-variants.md`. `agent-api-limitations.md` is history (what failed when only `fields` was tried), not a rule: context-only components are still not addable to a page body (header/footer come from the partial designs), component removal and moving ARE available (`remove_component_on_page`, `move_component_on_page`), variants and datasources ARE set (see below).

## Rules
1. Before every MCP write: `node harness/scripts/guard-customer.mjs sitecore-path <customer> "<item path>"`. Stop on ❌. Pages are only ever created under `/sitecore/content/<collection>/<site>/Home` of THIS demo's site.
2. **Existing components are reused as they are on the Sitecore side.** Use rendering ids from the manifest (`docs/ai/manifests/sitecore-manifest.yaml`, shared layer only). Site-level ids (Home, Data folders, variants) come from `site-manifest.json`, never from the manifest's `main-website` entries. Never create or edit renderings, templates or datasource templates for a component whose manifest status is `complete`. Only NEW components (no manifest entry) are registered under /sitecore/layout, via their create-* skills.
3. Resume-safe: before creating anything, look it up (`get_content_item_by_path`). Record every id in `demo-progress.yaml` → `pages[]`.
4. Parents before children, in `site.pages` order.

## Steps
**1. Resolve the site.** `get_content_item_by_path("/sitecore/content/<collection>/<site>/Home")` → `homeId`. Page templates come from `site-manifest.json` → `pageTemplates` (the DERIVED templates created by bootstrap step 4, which inherit the shared ones). Use the derived id for the page's `pageType`; fall back to the Home page's template or the registry only if `pageTemplates` has no entry, and say so.

**2. Create the first sub-page only, then check it.** Create the first non-Home page:
`create_page(name=<last path segment>, parentId=<parent page id>, templateId=<page template id>)`.
**Display names are mandatory.** The item NAME stays lower-case-hyphen (`contact-us`); the display name is DERIVED MECHANICALLY from the item name: hyphens become spaces and the first letter of EVERY word is upper-case (`contact-us` → `Contact Us`, `what-is-corrosion` → `What Is Corrosion`; the plan's `displayName` only overrides when the prospect's menu label differs, e.g. `FAQs`). Pass it when creating the page (`create_page(..., fields={"__Display name": <displayName>}, language="en")`) and, if the read-back does not show it, set it with `update_fields_on_item(itemId, {"__Display name": <displayName>})`, then `update_content(itemId, siteName, fields={"__Display name": ...}, language="en")`. The field is versioned and per language, so write it in the language version the page was actually created in: read the item's languages from `get_content_item_by_id` first, do not assume `en`. If all three MCP writes read back unchanged, use route 4: `node harness/scripts/layout-variant.mjs set-field --item "{id}" --field "__Display name" --value "Contact Us" --language <lang>` (Authoring GraphQL; needs `SITECORE_CM_HOST` and the automation client; prints OK only when the read-back matches). If every route fails, put a table `item path | display name to set` in `manual-tasks.md` and continue. ALWAYS read it back with `get_content_item_by_id(itemId, language=<that language>)`: if the tree label is still the item name (an earlier demo run: `about-us` instead of `About Us`) the write did not stick, so do not move on. Do the same for Home and for datasource items whose name is not readable. Then set the page fields (`Title` and the SEO fields listed under `inheritedFieldsUsed` in the registry) with `update_fields_on_item`, using field names from `get_content_item_by_id`.
Do NOT ask the SE and do not wait for a host. Check structurally: `get_content_item_by_id` shows the derived template and fields, and the Page Design mapping (bootstrap step 5) covers this page's template. Put "open /<path> and confirm header, footer and navigation render" in `manual-tasks.md` as the visual check, and continue. If the Page Design mapping is clearly missing for this template, fix the mapping (do not add header/footer components to pages) and continue.

**0. Header-area extras (before the pages).** For every `site.chrome` entry with `delivery: new` (or `reuse` of a component not yet placed), place the component in the partial design placeholder named in its spec (`eyebrow-left`, `eyebrow-right` or `header-right`) with the same procedure as `demo-site-bootstrap` step 5: derived dynamic placeholder key `/headless-header/<name>-0-<host DynamicPlaceholderId>`, the placeholder name must exist in the set variant's code, client variant set via the ladder, `get_components_on_page`/read-back to confirm. `hardcoded-variant` and `not-built` entries need nothing here.

**3. Create the remaining pages** the same way, parents first, including the navigation pages (`navTarget: true`): these mirror the prospect's header menu, get their `displayName` from the menu label, only the planned placeholder `PageHeading` (if any), and set whatever navigation fields the page template has (see `page-template-registry.yaml`: show in navigation, navigation title). **Every page (story pages and Home's children included) gets the `NavigationFilter` field set** (rule and ids in `demo-site-bootstrap` step 5b, ids from `site-manifest.json` → `navigationFilters`): a page is left visible in the Main Navigation ONLY when its plan `navGroup` is `main` and it sits directly under Home; EVERY other page (`eyebrow`, `none`, second-level dropdown children and anything deeper) gets `Main Navigation` ticked (`<id>`, several ids joined with `|`). That is what keeps the header menu to the prospect's top-level items; the eyebrow links are hardcoded in the client Eyebrow variant and need no page flag. Every page gets the field written, not just the first. Write it with `create_page(... fields)` or `update_fields_on_item`, and read one page back. Update progress after each. Do not stop between pages.

**4. Components per page, crop first.** Every page, /Home included, is built section by section from its own crops, and every page on a click path is built completely. For each page, for each section top to bottom (`sections[]`):
- **Open the section's crop first** (`component-crops.md`: the row for this page and position; `sections/NN-*.png` for /Home, `sections-<slug>/NN-*.png` for every other page). Build what the crop shows with the planned component: the registry component with the client variant / look, or the `fit: new` component built in phase 5. If the crop shows something the planned component cannot hold (more items, columns, images, a video, an accordion), STOP that section and build a new component for it (`sitecore-component-router`), update the plan section to `fit: new`, re-run `validate-site-plan.mjs` and `component-crops.mjs`, then place it. Reusing a component that drops what the crop shows is not allowed.
- **Rich Text never stands in for a component.** Rich Text is only a simple title and/or paragraphs. Never a list, cards, an FAQ, a logo wall, a video, buttons, images or columns, and never section HTML pasted into a Rich Text or Text field. P16 (`validate-site-plan.mjs`) and `component-crops.mjs` fail it, and `run-gate.mjs` re-runs both.
- **The section's component is the one in the plan.** Place that rendering. Do not replace it with Rich Text, and do not write the section's layout as HTML in a Text field. Rich Text is placed only when the plan's component is `rich-text` (a heading and paragraphs). If the planned component cannot be placed, build the one marked `fit: new`, or stop that section. There is no third option.
- **Content rules.** Fill only what the prospect's section shows (`sections.json` `order`). A Link field the prospect does not show stays EMPTY: no placeholder URLs such as `https://example.com`, no leftover second link. A link target is the prospect's real `href` or a planned page. Hero and section images come from `sections.json` (`images[].src` and `backgroundImages`, CSS backgrounds included) via `collect-images.mjs` → `content-hub-upload.mjs` / `media-upload.mjs` (`demo-build-content` step 3). **Uploaded is not attached:** every image of a planned section ends up in that component's Image field (its `imageFieldXml`). After the components of a page are placed and wired, run `node harness/scripts/attach-images.mjs <customer> --page <path>` (dry run), review `attach-images.md` and make each proposed write with `update_fields_on_item` (R5; `--apply` writes them directly and is only for when the MCP refuses): it matches each live image by its URL to its upload and writes it into the component's empty Image fields, in order, and reads them back. A section it lists under "Cannot attach" because the component has no Image field has the wrong component (Rich Text never carries imagery): fix the component, not the image. The section compare fails with `IMAGES` while a built section shows none of the prospect's images, and `run-gate.mjs` does not waive it. Never bulk-download images under generic names: the manifest entry keeps its live URL (`src`) so it can be traced back to its section. Never leave Default's sample images or text in a field the variant renders. The footer datasource is included: a field still equal to the Footer template standard value (`Why PLAY! finance`, `Copyright © Sitecore`) is sample content, and the page is not done.
- Create the section's datasource item FIRST, under `/sitecore/content/<collection>/<site>/Data/<component folder>` (`demo-build-content` step 4; MCP, R5). Then place the component: `add_component_on_page(pageId, componentRenderingId=<manifest rendering id>, placeholderPath="headless-main", componentItemName="harness-tmp-<n>", insertAfterComponentId=<previous>)`. NEVER pass `fields`: `add_component_on_page` creates a PAGE-LOCAL datasource `<page>/Data/<componentItemName>` and `fields` would fill that item, which is how an earlier demo run ended up with all its content under `Home/Data` instead of the site's `Data`.
- Wire the real datasource: `set_component_datasource(pageId, componentId, datasourceId=<id from content-map.yaml for THIS page + section>)` (if the tool refuses, `placeholders-and-variants.md` section 2). The id must belong to an item under the site's `Data` tree. Then remove the page-local item that `add_component_on_page` created: get its id first (`get_components_on_page` right after adding shows the new instance's local datasource), and after the re-point `get_content_references(<local id>)` must show no component referencing it, then `delete_content(<local id>)`. Only items you created under `<page>/Data` (name `harness-tmp-*`, or one named after the component) are deleted, never anything else.
- **Local-data audit (mandatory, end of each page and again for the whole site in step 7):** `get_content_item_by_path("<page path>/Data")` must not exist or have no children; delete leftovers as above. `get_components_on_page` must show every datasource path starting with `/sitecore/content/<collection>/<site>/Data/` (the Header/Footer partial designs' own `Data/Header` / `Data/Footer` are the only exception).
- **Content-resolved check (every component, right after the datasource is set; a component that renders empty is a failed step):** `get_components_on_page(pageId, includeRenderingDetails=true)` must show the datasource id AND resolved content (`isContentResolved: true` / the fields present, if the tool exposes them); also `get_page_html` (or the preview) must contain the section's title text. If it does not, work down this list and re-check after each: (1) the datasource item lives under THIS site's `Data/<component folder>` (`/sitecore/content/<collection>/<site>/Data/...`), not under a page's `<page>/Data` and not in another site: move it by recreating it there with `create_content_item` and re-pointing with `set_component_datasource`; (2) its template is exactly the rendering's Datasource Template (`get_component(<rendering id>)` vs the item's template id). Recreate the item with the right template under the site `Data` folder (`create_content_item`) and `set_component_datasource` to it; (3) it has a version in the page language with the fields saved (`get_content_item_by_id(id, language)`); (4) the datasource is referenced by item id; re-run `set_component_datasource`; (5) an INVALID FIELD VALUE (`node harness/scripts/link-audit.mjs <customer>` names the item, the field and the fix): a link field holding a raw string such as `/brands`, or `linktype="internal"` with a `url` (a path such as `/courses-by-program`) and no item `id`, or an image field holding a URL, makes the layout service drop the whole datasource (`isContentResolved: false`). Fix that field in place. An internal link is `node harness/scripts/link-xml.mjs make --text "<label>" --id "{GUID}"` (no `url`). An external link is `make --text "<label>" --url https://...`. `link-xml.mjs check` must print ok before the value is written. Do not change the rendering because the fields did not resolve. Re-check the same component; (6) compare with a component on the same page that DOES resolve: parent path, template, language versions, rendering parameters. Write the comparison to `<demo folder>/datasource-diagnostics.md` and carry on. When a component's datasource keeps failing, say so in `manual-tasks.md` with that comparison. Never leave the page at 'components render but show no content' without having tried (1)-(5).
- A new site's /Home starts with whatever the site template placed on it: re-wire what the plan keeps (match by component name and order), add the missing ones, and REMOVE the leftovers the plan does not keep with `remove_component_on_page` (one per call; confirm; re-read with `get_components_on_page`; components that come from the Page Design/partials are not removable on the page and are left alone). Only leftovers that could not be removed go on the manual list. If order is wrong, `move_component_on_page`.
- New sub-pages start empty, so nothing needs cleaning.
- Header and footer are added only through the Header and Footer partial designs (bootstrap step 5, template `{FD2059FD-6043-4DFE-8C04-E2437CE87634}`). They are not added to a page with `add_component_on_page`, and their `<r>` nodes are not written into a page's `__Final Renderings` or `__Renderings`. An empty `headless-header` means the partial is missing or is a folder (template `{C3CEB23C-D66D-4EF5-99E0-D45F60C02583}` is the Partial Designs folder, not a partial design): recreate the partial on `{FD2059FD-6043-4DFE-8C04-E2437CE87634}` and fix the Page Design mapping. Do not copy the chrome onto the page.
- Pages built on a derived template may inherit presentation from the shared standard values (e.g. an Author Widget whose datasource points at another site's author). Check `get_components_on_page` on the first article page: re-point such datasources to an item you created under this site's `Data` (`set_component_datasource`), or remove that component with `remove_component_on_page` if the plan does not keep it; list it as manual cleanup only if both fail. Never leave another site's item wired in.
- If `add_component_on_page` fails because a branch/insert template is missing in this environment (e.g. `/sitecore/templates/Branches/Project/Verticals/Questions`), do not invent the branch; skip that component, record it under "environment gaps" and tell the SE.

**5. Variants — set them, do not list them.** First run `node harness/scripts/variants-verify.mjs --customer <c> --fix`: a variant may only be SET on a page when the app exports it (otherwise the page renders "Content SDK component is missing React implementation"); the script adds a safety-net alias for any missing export and lists what is still alias-only (list those under `## Info` in `manual-tasks.md`, R4; the real variant is still owed: variants-verify --strict fails on aliases). EVERY placed component gets the demo's client variant (`site.variantName`, created in phase 5.5 by `sitecore-create-demo-variants`), never the shared `Default`; a section with a `look` gets `<variantName><look>` (e.g. `AcmeCorpImageLeft`) instead: after the component is placed and its datasource is wired, set the variant with the method ladder in `placeholders-and-variants.md` section 3, MCP route first (R5: the layout XML written with `update_fields_on_item`); `layout-variant.mjs apply` only when the MCP refuses, as recorded under "Verified methods" in `harness/reference/marketer-mcp-tools.md`. The variant id comes from `site-manifest.json` → `variants.<Component>.<ClientName>`. Batch the XML route per page: one read of the page layout, patch every needed rendering with `harness/scripts/layout-variant.mjs patch`, ONE write, one read-back. Confirm each with `get_components_on_page`. Only a section whose three routes all failed goes into `variant-checklist.md` (page path, position, component, needed variant, variant id) and `manual-tasks.md`.
**Read back ALL of them.** After step 5, `get_components_on_page` on EVERY page that has a non-Default variant (including every title-only stub with its look) and list page → variant in `variant-checklist.md`. If a page's variant is not what the plan says, step 5 is not done. Do not use a script or background job for the write (see the Bulk rule in `placeholders-and-variants.md` section 3).

**6. Links and navigation.** Every CTA/nav link in the content must target a planned page. Link fields hold LINK XML, never a path string: for each datasource link whose target is a planned page, set the field to `node harness/scripts/link-xml.mjs make --text "<label>" --id "{<page id from site-manifest/progress>}"` (internal link) with `update_fields_on_item`, replacing the placeholder written in content phase 3; re-read one to confirm. Then **`node harness/scripts/link-audit.mjs <customer>` must exit 0.** It reads EVERY item of the site from Sitecore (pages, `<site>/Data`, the partial designs' `Data`) and checks every General Link and Image field by its field type, whatever wrote it. A literal value (`/about-us`) or an internal link with no `id` (only a `url="/path"`) makes Sitecore drop the whole datasource (a `url` NEXT TO the id, as Sitecore's link picker writes it, is fine), so the component renders empty. For each failure the script prints the exact fix (`link-xml.mjs make --text "..." --id "{page id}"`, the page resolved from the path): write it with `update_fields_on_item`, read back, re-run until clean. Do not clear a field to hide the failure, and do not swap the component. Without an Authoring GraphQL client (exit 3) do the same sweep with the MCP (`get_content_item_by_id` on every datasource item, `link-xml.mjs check` per link field) and write `<demo folder>/link-audit.json` as `{ "source": "mcp", "items": <n>, "linkFields": <n>, "bad": [] }`: `run-gate.mjs` reads it. An image field that is not image XML is corrected the same way. After creating pages, check: does the site's main navigation list the new pages? If navigation comes from a datasource or settings item (see `.skills/sitecore-reference/references/sitecore-content-resolvers.md`), update it with `update_fields_on_item`; if it cannot be set by API, put one line in the manual-task list.

**7. Verify.** For each page: `get_components_on_page` → compare to the plan (component + order), check every datasource is non-empty and lives under the site's `Data`, report gaps. A page whose `headless-main` renderings are not the plan's components, in order, is not done. `run-gate.mjs` reads what is really placed from the app's content endpoint (the preview context in the app's `.env.local`, which serves master: no publish needed during development; publishing is only for the deployed Vercel site) and compares it with the plan. There is no file fallback. For your own record you may still write `<demo folder>/placed-components.json` from the `get_components_on_page` responses, verbatim (never from the plan): keys are plan paths (`/Home`), values are the `componentName` list from `headless-main` only, in order. Header and footer are not in the list. `run-gate.mjs` compares this file to `demo-plan.yaml` and fails on a mismatch; nothing in `manual-tasks.md` waives it. Then the SITE-WIDE sweeps, all of which must pass before the hand-over: (a) **no page-local data**: every page (Home included) has an empty or missing `<page>/Data`; (b) **display names**: every page's `en` display name equals the plan's `displayName`; (c) **navigation**: only `navGroup: main` pages directly under Home lack the Main Navigation tick, every other page has it; (d) **variant code**: `variants-verify.mjs --customer <c>` exits 0 and, for every placed component, the selected variant is exported by its file, and each placed component's Headless Variants container is named like its rendering item; (e) **header**: the built header matches the prospect's (`sitecore-create-demo-variants` step 7, `header-styles.mjs --compare`). Fix what fails (delete, re-write, re-run) and re-check. Mark `pages[].status: verified`. Then the section gate for EVERY mirrored page (`sitecore-create-demo-variants` step 7 items 3b-3c), each page's verdict against its own `sectionsFile`. Finally run `node harness/scripts/run-gate.mjs check <customer>`: the build is not done until it exits 0.

**8. Thumbnails: NOT uploaded by the run.** Do not screenshot the site or upload a thumbnail (`sites-api.mjs upload-thumbnail` stays available for manual use only). ALWAYS write these three lines into `manual-tasks.md` (section "Always"), whatever else happened:
- [ ] Add site thumbnail
- [ ] Add partial thumbnails
- [ ] Update layout icons (only if a NEW component was created, rather than new variants)

## Output
- `pages[]` in `demo-progress.yaml` all `verified` (or the failures listed)
- `variant-checklist.md` (per page)
- Manual-task list: only what failed (variants all routes failed on, Home leftovers `remove_component_on_page` could not remove, navigation if needed)
- `datasource-diagnostics.md` when a datasource needed repair; the sweep results of step 7 (counts of page-local items deleted, display names fixed)
- Page URL list for `demo-script.md`: `<site hostname>/<path>` for each planned page
