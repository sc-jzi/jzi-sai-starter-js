# Build a demo from a discovery transcript (new site from scratch, multi-page, story-first)

Use when the SE gives a discovery-call transcript (Gong export) and wants a demo site: "build a demo from this transcript", "new demo for <customer>".
It decides WHAT to build (story, pages, sections), then creates a NEW Sitecore site from scratch (new or existing collection, never a copy of another site) and builds every page.
Method: `harness/reference/demo-method.md` (Chain of Pain, AAA, Command of the Message, do the last thing first). Read it first.

## Hard rules (never break)
1. **Only the customer's own folder and its own new site change.** Never edit `industry-verticals/prospera` (the base app) or another customer's folder, and never touch an existing site (ProsperaFinancial included). **No site is ever duplicated, copied, renamed or moved.** Run `node harness/scripts/guard-customer.mjs check <customer>` after every phase. Before EVERY Marketer MCP write: `node harness/scripts/guard-customer.mjs sitecore-path <customer> "<item path>"`; stop on a failure.
2. **One approval gate** (Phase T4). Do not ask permission step by step afterwards. Stop only on a failed check or an irreversible decision.
3. **Never invent facts.** Pains, quotes, numbers and names come from the transcript, marked *stated* or *inferred*. Gaps stay gaps. Figures not from the transcript or the customer's site are labelled illustrative.
4. **Inputs are never committed** (transcript, RFP files and supporting material are stored git-ignored by `intake-materials.mjs`). Quote at most a sentence per row; RFP content is confidential, so never paste whole documents into chat.
5. **Settings and secrets come from `harness/.env.local`.** Never ask the SE to paste secrets into chat.
6. **Existing components are reused as they are on the Sitecore side** (shared templates, renderings, rendering parameters under the project layer). Only the code files are replaced in the customer copy. Register something under /sitecore/layout only for a component that is NEW (not `status: complete` in the manifest).
7. English-only content, Marketer MCP field-name rules and Agent API limits still apply (`.cursor/skills/sitecore-reference/references/agent-api-limitations.md`).
8. **Other demos are invisible.** Never open, search, list or copy from another prospect's folder under `industry-verticals/` (their plans, manual tasks, progress files, transcripts): nothing in them is yours to reuse and they bias the result. Everything you need is in the plan template, the skills, `harness/reference/` and the read-only base app `industry-verticals/prospera`. What you learn the hard way (tool shapes, ids, workarounds) goes into `harness/reference/marketer-mcp-tools.md` → "Verified methods" before you move on: that is the ONLY shared memory between demos.
9. **Measurements are never hand-edited.** `nav.json`, `header-styles*.json`, `sections*.json` come from the scripts only. A wrong result is fixed by re-running with the script's override (`nav-extract --root "<css>"`, `header-styles --eyebrow/--main "<labels>"`, `section-capture --selector "<css>"`) or, if the script itself is wrong, reported in the hand-over as a script fault. Editing a reference JSON (or the demo JSON) so that a looks gate goes green is a lie to the gate and is forbidden.
10. **Scratch scripts** go in `<demo folder>/tmp/` (never in `harness/scripts`, never named after a prospect). On Windows PowerShell, inline `node -e` / here-strings mangle quotes: write a `.mjs` file and run it. Timestamps in `demo-progress.yaml` come from the real clock (`new Date().toISOString()`), never typed from memory.
11. **No fire-and-forget Sitecore writes.** Writes to Sitecore (variants, fields, pages) run in the foreground, one result checked per item. A script or background job that exits non-zero, or a read-back that disagrees, is a FAILED step: fix it before saying the work is done, and never report "built" for something a failed job was meant to write. Only the app dev server runs in the background.
12. **A front-end workaround for a Sitecore feature is disclosed.** Code that imitates a Sitecore behaviour (for example a cookie that drives personalization because Edge does not apply the page-visit rules until publish) is allowed only when Sitecore's own mechanism cannot work on the demo host. The Sitecore rules are still built; the workaround is named at the approval gate under "Personalization / behaviour" and in `demo-script.md`, with what the SE must do instead in Pages (for example preview the persona).

## Continuous run: no unscheduled stops
From the moment the SE approves the plan until the hand-over in Phase T6, the run does not stop, hand back, or ask. It is one continuous run, even if that takes a long time.
- **Never end your turn with a status summary or "say resume demo" between phases.** The only message after approval is the T6 hand-over. (Use the task list for progress; that is what the SE watches.)
- **Core work is BUILT, never deferred.** The SE must never have to do build work by hand. Core = partial designs, page designs, derived templates, datasources (in `<site>/Data`), variant CODE, the applied theme, images in Content Hub with a public link attached to the datasources, the per-page navigation flag, display names, the measurements and the looks gates. If a step fails: fix the cause and retry, then try the next route (the ladders in `placeholders-and-variants.md`). Only after TWO different routes failed may the item go into `manual-tasks.md`, and only as `BLOCKED after 2 attempts: "<exact error>"` under "Open"; everything that does not depend on it carries on. "Not created yet", "not written yet", "cannot be done" without two quoted errors is NOT acceptable.
- **What may be a manual task:** the editing host (Sitecore CLI missing or not logged in), the three fixed "Always" lines (thumbnails, layout icons), and what only a person can do (a login, a licensed font file). Nothing else.
- **The run is finished only when `node harness/scripts/run-gate.mjs check <customer>` exits 0.** Run `run-gate.mjs init <customer>` at the start (creates `manual-tasks.md` with the fixed "Always" section; never rewrite that section). Before ANY hand-over or end of turn after approval run `check`; exit 4 prints what is unfinished and the next action: do it, then re-run. Never end a turn, summarise or hand over while it exits 4. If the turn is cut (tool-call limit, timeout), the next message "resume demo" restarts at the first failing gate item, so keep `demo-progress.yaml` current after every phase.
- **No host needed to build.** Everything the build does goes through the Marketer MCP, the Sites API and the local app files. The editing host is only needed to LOOK at pages in Pages or on a deployed site; its absence never blocks content, components, datasources, theme or pages. Verify structurally with `get_components_on_page` and `get_content_item_by_id`; leave visual checks for the SE in `manual-tasks.md`.
- **Never ask the SE a question after approval** unless a later step is impossible without the answer AND nothing sensible can be assumed. If you must assume, assume, write the assumption into `manual-tasks.md` under "Assumptions" and continue. An assumption is a decision that neither the prospect's site, the transcript nor the SE made; it is never a statement about what the demo is ("the demo mirrors X") and never a justification for invented content.
- **Stop only when** (a) the same step fails twice and everything after it depends on it (site not created, no Home page, shared component layer missing), or (b) an action would touch something protected. Then say exactly what failed, what exists, and the one thing that unblocks it.
- If the shell or tool times out, retry once, then record it and continue with what does not depend on it.

## Phase T0 — Preflight
- `node harness/scripts/env-check.mjs` passes. If `harness/.env.local` is missing or a required value is empty (Content Hub values when `CH_ENABLED=true`): tell the SE exactly which values to fill in, then stop.
- Demo documents open as a rendered preview, not raw markdown (if `.vscode/settings.json` is blocked for the agent, skip this silently and just tell the SE "Ctrl+Shift+V previews them"): make sure `.vscode/settings.json` has `"workbench.editorAssociations": { "**/docs/ai/demos/**/*.md": "vscode.markdown.preview.editor" }` (add it, keeping the other settings, if it is missing).
- If `harness/reference/marketer-mcp-tools.md` does not exist: write it from the Marketer MCP tool list you can see (every tool name with its parameters, one line each, marking any parameter that sets rendering parameters / variant / display name, or that accepts a partial design or other non-page item id). Read-only; it records what this environment's MCP can really do and is used by the bootstrap and build skills.
- `node harness/scripts/deps-check.mjs --fix`: checks Node, git and Playwright + Chromium (in `harness/`) and installs what is missing itself. Tell the SE only if it still fails after the fix. (The customer app's packages are checked later, once its copy exists: see `demo-new-site`.)
- `<customer>` = lower-case kebab name, also the folder under `industry-verticals/` (e.g. `acme-corp`). It must not be `prospera` or in `PROTECTED_FOLDERS`.
- `node harness/scripts/guard-customer.mjs snapshot <customer>`
- `.cursor/hooks.json` must exist (a `stop` hook running `node harness/scripts/run-gate.mjs hook`): after approval it restarts the run automatically while the gate is red. If Cursor's Hooks are switched off the SE enables them in Cursor Settings → Hooks; say so once in the T0 message, do not stop for it.
- `node harness/scripts/run-gate.mjs init <customer>` (creates `manual-tasks.md` with the fixed "Always" lines)

## Phase T1 — Intake
`node harness/scripts/intake-materials.mjs <customer>` takes EVERYTHING in `harness/inbox/` (or specific files with `--file <path>`, repeatable): Gong transcript, RFP documents (Excel, Word, PDF, any mix) and supporting material (brand guidelines, product sheets, screenshots, logos). Each file is stored under `industry-verticals/<customer>/docs/ai/demos/<customer>/inputs/` (git-ignored), and every Excel/Word/PDF/text file is converted to `inputs/extracted/<name>.txt` (Excel rows as `R<row> | cell | cell`, all sheets, hidden ones marked). `inputs/index.json` lists the files with a GUESSED kind (`transcript` / `rfp` / `image` / `supporting`) from the file name.
Then READ the extracted text of every file (not just the first), confirm each file's kind from its content, and fix `index.json` if the name misled. If a PDF has no text layer, open the PDF itself and read it visually. If the dependency check reported missing readers, run `node harness/scripts/deps-check.mjs --fix`. If the files obviously belong to different prospects, stop and ask which belongs here.
**Nothing at all?** Run `node harness/scripts/intake-materials.mjs <customer> --none` and do the interview in Phase T2 instead. Never invent a transcript or RFP, or fill the brief from guesses.

## Phase T2 — Draft the brief
**With a transcript:** read it and fill `harness/templates/demo-brief.template.md` → `industry-verticals/<customer>/docs/ai/demos/<customer>/demo-brief.md`: Audience (AAA), Chain of Pain ranked by emphasis (owner, reason/source, quote, stated/inferred, impact only if given), message map, demo flow with moment 1 = the last thing first (3–6 moments, each with CBI, audience, annoyance → afterward, capability, must-be-visible, check-in question), situation slide, recap. If the SE supplies a colleague's discovery/demo-flow prompt, follow its sections but keep these fields.
**RFP-led brief (an RFP exists, with or without a transcript):**
1. Build `.../<customer>/rfp-requirements.md`: one row per requirement or question in the RFP files, with `id` (R-001...), the requirement in a short paraphrase (keep the RFP's own wording for demo scenarios), `source` (file / sheet / row or page), `category` (DEMO scenario or script request, functional, technical, security/compliance, commercial, other), weight or priority if the RFP scores it, and `coverage`: *shown* (in which moment and page), *partly*, or *written response only* (not demonstrable in a site demo, with a reason). Process every sheet, every row and every page; say how many requirements there are in total.
2. The RFP's own demo requirements (scenarios, scripts, order, time limit, attendees) are the spine of the demo flow. If the RFP prescribes an order, keep it; otherwise apply "last thing first". Merge scenarios that one page can prove, but never drop a mandatory (must-show) requirement silently: if it cannot be shown, list it with the reason at the gate.
3. Without a discovery call there are no quotes from the customer. Pains and the audience come from the RFP (stated goals, evaluation criteria, named roles, stated problems) and are marked evidence type **`rfp`** with file / sheet / row as the evidence, or *inferred* when you are reading between the lines. A transcript, if present, still supplies *stated* pains and quotes. Anything neither source says is a gap: ask the SE (Phase T2 gaps question; `demo-interview.md`, "With an RFP but no discovery call").
4. Supporting material (brand guidelines, product sheets, screenshots, logos) feeds the theme proposal (Phase T3b: colours, fonts, logo), real content and page ideas; cite the file name. Do not invent content that none of the files, the prospect's site or the SE supplied; label illustrative content as such.
5. Fill the brief as usual and complete its "Inputs" line and RFP section. `evidenceType` in `demo-plan.yaml` accepts `stated`, `rfp` and `inferred`.

**Without a transcript or RFP (interview):** ask the SE the questions in `harness/templates/demo-interview.md` (at most 4 per `AskUserQuestion`, free text welcome; skip what the SE already said in the request). Fill the same brief from the answers; every fact is marked *stated by the SE*, and anything the SE does not know stays a gap (do not infer pains or numbers). If the SE already has a demo flow or a discovery prompt, take it as the starting point and only ask for what is missing.
Also collect any real gaps that block the story (a screenshot when the site blocks capture; the customer URL only if it cannot be found, see the mirror rule) in ONE `AskUserQuestion` (max 4 questions), then the Sitecore choices below.

### Sitecore choices (always ASK; never decide yourself)
Do not pick the collection or the site template for the SE, not even when only one exists and not "to keep things simple". Ask with `AskUserQuestion`, options built from the live environment:
1. `node harness/scripts/sites-api.mjs auth-check` first (it prints the environment and the collections it can see). If it fails, stop and say so.
2. **Collection**: options `New collection named "<Customer>" (Recommended: nothing shared with other demos)` and `Use an existing collection`. Put the collection names found in this environment in the question text so the SE can tell if it is the wrong environment. If existing: ask which one (options from `sites-api.mjs collections`, max 4 + Other).
3. **Site template**: `node harness/scripts/sites-api.mjs templates`. Options are template NAMES (never ids), `Empty` first labelled `(Recommended)` when it exists, then the others (max 4 options, rest via Other). All sites in an existing collection must use the same template: when the SE chose an existing collection, say which template its sites use if you can tell.
4. Site name defaults to the customer's display name; it is shown at the gate, where the SE can change it.
Write the answers into `demo-plan.yaml`: `site.collection`, `site.collectionMode` (`new` | `existing`), `site.template` (the name), `site.siteName`.

## Phase T3a — Measure the prospect (mandatory when the prospect has a URL; never skipped)
Everything the build copies from the prospect's site is MEASURED first, in this order, into the demo folder. `validate-site-plan.mjs` (P13) and `run-gate.mjs` fail without these files.
1. `node harness/scripts/nav-extract.mjs --customer <customer> --url <prospect url> --hover` → `nav.json`. Check it against the homepage screenshot: the MAIN menu must not contain the utility links; if it does or a menu is cut off, re-run with `--root "<css selector of the main menu>"`.
2. `node harness/scripts/header-styles.mjs --customer <customer> --url <prospect url>` → `header-styles.json` (+ reference crop). Check the band heights it prints against the reference crop (a page-wide height means a wrong band): pass the real labels with `--eyebrow "A,B" --main "C,D"` and re-run.
3. `node harness/scripts/section-capture.mjs --customer <customer> --url <prospect url>` (a flat page is split into its bands automatically; `--selector` overrides) → `sections.json`, `sections/NN-*.png` (one crop per section: this is the per-component screenshot set the variant phase builds from), `sections.md`. For every other mirrored page (`liveUrl` on the page) capture it to its own file: `--url <live page url> --out sections-<slug>.json`, and name that file in the page's `sectionsFile` in the plan (its `liveSection` numbers refer to that file).
The SE's own crops in `<demo folder>/sections/` take priority over the script's. If the site blocks headless capture (exit 3) take the SE's inbox screenshots, cut them into `sections/` crops yourself, and write the numbers you can read into the same JSON shape; do not skip the step.

## Phase T3 — Derive the page tree and sections
Build `industry-verticals/<customer>/docs/ai/demos/<customer>/demo-plan.yaml` from `harness/templates/demo-plan.template.yaml`: copy the story, then write `site.pages`.
- Plan /Home as the first page. Whether the new site already has one depends on its template; `demo-site-bootstrap` probes it. Moment 1 (WOW) is on /Home or one click away.
- One page per thing a moment needs to show.
- **Click path per moment (`clickPath`, required, P15).** For each moment write the ordered pages the SE clicks through, starting at /Home, INCLUDING landing and intermediate pages and pages whose visit triggers personalization or other behaviour (a page the visitor must visit before the experience changes is on the path). Walk it on the live site: every step must be a real link or button on the previous page (a dropdown-only child is reachable only if the landing page or a section links to it: plan that link in the section). Every page on a clickPath is a visited page, so it mirrors its live page (P14). Menu-only pages stay stubs. Print the clickPath per moment at the gate.
- **Information architecture = the prospect's header menu.** Run `node harness/scripts/nav-extract.mjs --customer <customer> --url <prospect url> --hover` (writes `nav.json`; check it against the homepage screenshot, because mega menus and JS menus can come out incomplete; also use the AE notes and transcript for menu items they mention). Every top-level item of the MAIN menu (Login included: it is a page) and every item in its dropdown (two levels, max 40 pages in total) becomes a page under /Home, nested the way the menu is nested; skip search/language controls and external links. The small utility bar ABOVE the header (`eyebrow` in `nav.json`: e.g. About us, Join our team, Locations, Contact us) is a separate group: plan those as pages too, with `navGroup: eyebrow`. **The eyebrow bar is HARDCODED in the client Eyebrow variant** (links, phone, search, CTA; generated by `header-kit.mjs`), it uses no Navigation component and no filter, so `eyebrow` only decides that those pages are NOT shown in the main menu. `navGroup: main` is ONLY for pages directly under /Home (top level of the main menu); dropdown children (second level and deeper) and all other pages are `navGroup: none` (the default). Only the top level of the main menu is ever shown in the header; deeper levels are built as pages but hidden from navigation (their `Main Navigation` filter is ticked). The phone number and CTA button (`eyebrowExtras`) are not pages. Never merge the two groups into one menu. Right after `nav-extract` run `node harness/scripts/header-styles.mjs --customer <customer> --url <prospect url>`: it MEASURES the prospect's header (sizes, colours, spacing; writes `header-styles.json` and `header-reference.png`) and phase 5.5 builds the header from those numbers, not from the screenshot by eye. Menu items that no moment needs are planned as **navigation pages**: `navTarget: true`, `navReason: "Header menu item"`, `proves: []`, a readable `displayName` (the menu label), and at most one section, a `heading-cta` / `PageHeading` carrying the title (`contentSource: illustrative`), so the page is not blank but is clearly a placeholder. They are built so the header navigation of the demo site matches the prospect's, and they are NOT demonstrated. If the menu was not readable, say so at the gate and build the story pages only. Then run `node harness/scripts/section-capture.mjs --customer <customer> --url <prospect url>` (writes `sections.json`, `sections/NN-*.png`, `sections.md`: per-section element order, colours, backgrounds, widths, images incl. CSS backgrounds, links). Use `site-analyzer` with it for the fit check; the SE's own crops in `<demo folder>/sections/` take priority over the script's crops. Hero/section images come from `sections.json` (`images[]`, `backgroundImages`) into `content-map.yaml`.
- Pages that prove no moment and are not menu items are not built.
- **Menu pages: stub or mirror, decided by whether the demo navigates there.** A menu item nothing in the story visits (`proves: []`, no `visit: true`) is a title-only stub with `look: PageTitle` (a heading-only variant, never one with empty fields that print "[No text in field]" in Pages). A page the story navigates to (a moment proves something there, or the SE says they will click through to it: set `visit: true`) is built as the live page: set `liveUrl` (from nav.json), capture it sequentially with `node harness/scripts/section-capture.mjs --customer <customer> --url <page url> --out sections-<slug>.json`, name the file in `sectionsFile`, and build its sections from existing components (reuse | variant | new, same fit check as Home; card lists use the closest repeating component with a `look`) with the live copy; P12 then applies. At the approval gate list the stubs and the mirrored pages separately and ask once: "Any other menu page you will click through to?" (those get `visit: true`). `validate-site-plan.mjs` P14 enforces this.
- Every page has `path` (name: lower-case, hyphens, alphanumerics only) AND `displayName` (the readable title, e.g. `what-is-corrosion` -> `What is Corrosion`). Page types: `page`, `article`, `landing` (confirm in `industry-verticals/prospera/docs/ai/catalog/page-template-registry.yaml`).
- **Fit check for every section AND every header-area feature (function first, look second; `.cursor/skills/site-analyzer/SKILL.md` step 4).** Each section carries `fit: reuse | variant | new` (+ `fitReason` for variant and new). `new` is for a missing FUNCTION or FIELD/ITEM SHAPE (search, locator, tabs, a list whose items need fields no registry list has, ...), never for a different look; a variant cannot add fields or behaviour. A `new` section has a `new:` spec (`name`, `kind`, `cms`, `fields`/`children`, `behaviour`, `placement`) instead of a registry id. Fill `site.chrome` from the prospect's header (eyebrow links/phone/search/CTA, language, login, cart, announcement bar, mega-menu): each feature is `reuse`, `hardcoded-variant`, `new` or `not-built` (with a reason). Never leave a feature the prospect visibly has and the story/look relies on out without saying so. `validate-site-plan.mjs` enforces the specs (P5, P10, P11).
- Otherwise sections use ids and variants from `industry-verticals/prospera/docs/ai/catalog/component-registry.yaml` (the variant named in a section is the BASE the code starts from; every component is then given the demo's own pixel-matching variant `site.variantName`; the header-area ones (Eyebrow, Header, Navigation) are generated by `header-kit.mjs` in bootstrap step 5, the rest are coded in phase 5.5) (matching rules: `.cursor/skills/site-analyzer/SKILL.md`). Header and footer are not sections. Each section has `contentSource`: transcript | site | illustrative.
- **MIRROR RULE (default, needs no instruction from the SE).** **Default assumption: the prospect has a live website and this demo is a skinned copy of it.** The SE never has to say so. The URL comes from the request, the materials or the transcript; if none is given, find the official site with WebSearch (company name in the materials) and use it; ask only when you cannot find it or several companies fit. "No live site to copy" is the exception and only when the SE says so (a startup, a new brand, a pure concept). **A URL you looked up yourself is VALIDATED before any other work** (no intake, brief, measurement or Sitecore call until it passes): open it (`WebFetch`, or Playwright if that is blocked) and confirm that (1) it loads (not an error, parked or redirect-to-other-company page), (2) the page title / about text / footer legal name matches the prospect's name from the materials, and (3) what the site does fits the industry, products or people named in the transcript/RFP/request. Say the result in the first message in one line: URL, what you matched it on. If all three hold, continue. If any is doubtful (similar names, several regional or brand sites, a parent company) ask ONE `AskUserQuestion` with the candidates (max 4) before doing anything else. A URL the SE gave is used as given (only check that it loads). A page that exists on the prospect's live site is BUILT AS THAT PAGE: /Home and every menu page that has a real counterpart (`liveUrl` on the page). Same sections, same order, same copy, same images, taken from `sections.json` and the extracted content (`content-extractor.mjs`), not from the story. Each section carries `liveSection: <# in sections.md>`. The story does not reshape a live page and invents no copy for it. Story-specific additions are allowed only where the demo moments truly need something the live site does not have: mark such a section `added: true` + `addedReason` (which moment needs it), keep it to the minimum, and list it at the gate under "ADDED (not on the live site)". Default is nothing added. Pages the live site does not have (story pages) are composed from the library using the moment, content marked `transcript` or `illustrative`.
- /Home and the other mirrored pages: `validate-site-plan.mjs` P12 enforces `liveSection` / `added`, P12b lists live sections that are not in the plan.
- `site:` (`collection`, `collectionMode`, `template`, `siteName`) comes from the SE's answers in Phase T2; do not fill it in any other way.

## Phase T3b — Theme proposal (shown at the gate, applied after it)
Nothing in an app or in Sitecore changes here; all files stay in the demo folder.
1. With the prospect URL: `node harness/scripts/site-scraper.mjs --url <prospect url> --output industry-verticals/<customer>/docs/ai/demos/<customer>/theme`. If the site blocks it or there is no URL, use the screenshot the SE gives (method and confidence rules: `.cursor/skills/sitecore-extract-theme/SKILL.md`, steps 2-4).
2. Write `.../demos/<customer>/theme/theme.yaml` (format: `industry-verticals/prospera/docs/ai/templates/client-theme.template.yaml`) and `.../theme/theme-proposal.md`: brand colours mapped to Prospera's `site-<customer>` variables (`.cursor/skills/sitecore-reference/references/site-theme-variables.md`) as a hex table, heading and body fonts (a Google Fonts substitute when proprietary), hero/card/button style, light or dark, the screenshot paths and a confidence line (high/medium/low and why).

## Phase T4 — Validate, then the single approval
```
node harness/scripts/validate-story.mjs <customer>
node harness/scripts/validate-site-plan.mjs <customer>
node harness/scripts/bootstrap-plan.mjs <customer>
```
Fix every ❌ yourself. Then **write the whole plan as normal chat text, and only then ask**. The question widget shows only the question, and the SE must not have to open tool output or files to judge the plan. Use the files as sources, but print everything below in the message itself, in this order:

1. **Story**: the situation in two lines; the inputs used (file names and kinds); for an RFP-led demo the coverage line ("N of M requirements shown, K written-response only, L partly", plus every mandatory requirement that is not shown and why); the ranked pains (id, pain, who feels it, *stated*/*inferred*); the demo moments (number, title, audience, what they see, and the click path as `/Home → /x → /y`; moment 1 marked *last thing first*).
2. **Theme**: table of the `site-<customer>` colours (variable → hex), heading and body font (plus the substitute when proprietary), tone, confidence and why, and the path of the screenshot to compare with the live site.
3. **Pages**: the page tree (story pages first, then the navigation pages that only mirror the prospect's menu, with their count), then for EACH story page a table: position, component, variant, content source (transcript / site / illustrative), moment it proves. Navigation pages are listed by name only. Mirrored pages (Home, ...) are listed section by section as "live section # → component"; anything with `added: true` goes in its own list headed **ADDED (not on the live site)** with the reason, or the line "Nothing added: the page mirrors the live site". Behaviour the story adds on top of a mirrored page (personalization variants, swapped sections, AI features) is listed too, under **Personalization / behaviour (not on the live site)**, with its rules marked illustrative.
4. **Components**: one table of every component used (name, variants used, on which pages) marked *reused* (already registered in Sitecore) or *new*, and anything that needs custom work.
