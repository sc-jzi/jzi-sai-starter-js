# Nested placeholders, datasources and headless variants — how to do them (nothing here is "not possible")

Used by `demo-site-bootstrap` (header/footer partials) and `demo-build-pages` (every page). The SE's requirement: components land in the CORRECT dynamic placeholder, every component that has a datasource gets it, and every component that needs a non-Default variant gets it. If the first method fails, go down the ladder; a manual task is the LAST resort and must name the exact method(s) tried.

## 1. Nested (dynamic) placeholders — derive the key, never hardcode it
A component that hosts other components (Eyebrow, Header, Container, Tabs, ...) renders placeholders whose key depends on the host instance. On SitecoreAI the key is
`<host's own placeholder path>/<placeholder name>-0-<host's DynamicPlaceholderId>`
Examples the SE confirmed in Pages: Eyebrow (DynamicPlaceholderId 1) → `/headless-header/eyebrow-left-0-1`, `/headless-header/eyebrow-right-0-1`; Header (DynamicPlaceholderId 4) → `/headless-header/header-right-0-4`. The numbers are NOT constants: they are the host instance's `DynamicPlaceholderId` and change with how many/which components were added before. Never copy them from this file, from another site or from a previous demo. The wrong forms `eyebrow-left-1` and `<name>-<id>-0` do not render anything (the component is stored but shows in no placeholder).
Procedure (every time a child goes into a host):
1. Add the host first (e.g. Eyebrow into `headless-header`).
2. Read it back: `get_components_on_page(pageId=<page or partial design id>, includeRenderingDetails=true)`. Take the host's `DynamicPlaceholderId` from its rendering parameters. If the tool does not show it, read the item's layout field (`get_content_item_by_id`, fields `__Final Renderings` / `__Renderings`) and take `DynamicPlaceholderId=<n>` from the host's `s:par`. If there is none at all, the host has no dynamic id yet: re-read after saving once; still none → treat the placeholder as non-dynamic (`<host path>/<name>`) and say so in `site-manifest.json` notes.
3. Take the child placeholder NAME from the host's code (`industry-verticals/prospera/src/components/**/<Host>.tsx`, the `<Placeholder name=.../>`/`getPlaceholder` call; the variant that is selected matters: Header `WithLogoImage` has only `header-right`, `Default` has `header-left` + `header-right`).
4. Build the key with the formula above. Check it with `get_allowed_comps_by_ph(pageId, placeholderName=<key>)` (must list the child's rendering) and, if the reference site has the same host with children, compare the format with its stored `s:ph` values (read-only).
5. `add_component_on_page(..., placeholderPath=<key>)`. The API accepts any string, so a wrong key does not error: re-read with `get_components_on_page` and confirm the child's placeholder equals the key. A mismatch is a failed step: fix it (re-add under the right key) before moving on.
6. If the key above is rejected or the child is orphaned, try the neighbouring forms ONCE each (no leading slash on the leaf, `-<id>` only), keep whichever is accepted AND shown by `get_components_on_page` under the host, and write the working format into `harness/reference/marketer-mcp-tools.md` → "Verified methods".

## 2. Datasource (and every other instance property) of a placed component
Everything that is stored ON a placed rendering instance is written with the SAME ladder as the variant in section 3: the datasource (`s:ds`), the variant (`FieldNames`) and any other rendering parameter (`NavigationFilter`, `Levels`, `Styles`, ...). Order: (1) the tool (`set_component_datasource(pageId, componentId, datasourceId)`; `pageId` may be a page or a partial design id); (2) layout XML through the MCP: `layout-variant.mjs patch --xml-file <layout field value> --uid <rendering uid> --ds <datasource id> [--variant <id>] [--param Key=Value ...]` (it patches `s:ds`, `FieldNames` and any `s:par` key in one pass and preserves everything else), written back with `update_fields_on_item`, same backup and read-back rule as route 2 of section 3; (3) `layout-variant.mjs apply` (Authoring GraphQL).
**A refusal from the tool is not an answer.** `set_component_datasource` answers "No datasource template found for component" (or similar) for renderings whose Datasource Template is empty (context-only: the shared Header, Navigation, Footer variants). That is the TOOL's own check. Sitecore itself stores `s:ds` on any rendering instance: in Pages the SE picks the Header's data item by hand and it works. an earlier demo run stopped at this message ("the Header rendering has no datasource template ... Both Navigation renderings have the same limit"), left the Header without its logo item and the Navigation without Home, and wrote it off as a limitation. It was not one. For context-only renderings go STRAIGHT to route 2.
What each needs: Header → its `Data/Header` item; Navigation (header) → the site's Home item (the Navigation Contents Resolver lists the pages below its datasource); a component with a real datasource → the item from `content-map.yaml`. After writing: the layout XML (re-read) shows `s:ds` on that instance AND `get_components_on_page` / a page screenshot shows the effect (logo visible, navigation listing pages). An empty datasource on a component that needs one is a failed step.

## 3. Headless variant of a placed component (`FieldNames` rendering parameter)
The variant is stored on the rendering instance as `FieldNames={<variant definition item id>}` in `s:par` of the layout XML (`__Final Renderings` for versioned layout, `__Renderings` for shared layout). The variant definition ids come from the site's `Presentation/Headless Variants/<Component>/<Variant>` items (created in bootstrap step 2, recorded in `site-manifest.json` → `variants`). Method ladder — stop at the first that works and VERIFY by reading back:
1. **Tool argument.** Look at the live Marketer MCP tool list (the same one `harness/reference/marketer-mcp-tools.md` was generated from). If any tool now has an argument for rendering parameters / variant, use it. Regenerate `marketer-mcp-tools.md` if the list changed. As of the 2026-10-12 release none does: `add_component_on_page` takes `fields` (datasource fields only), `insertBeforeComponentId`/`insertAfterComponentId` and `placeholderPath`. `set_component_variant` / `reset_component_variant` / `list_page_flows` are for A/B/n tests and personalization (copy/hide/swap inside a flow), NOT for headless variants: do not call them for `FieldNames`.
2. **Layout XML through the MCP.** `get_content_item_by_id(<page or partial design id>)`, find the field that holds the component (its rendering `uid` from `get_components_on_page`), save the original value to `<demo folder>/layout-backup-<id>.xml`, patch it WITHOUT touching anything else:
   `node harness/scripts/layout-variant.mjs patch --xml-file <saved field value> --uid <rendering uid> --variant <variant definition id>` (prints the patched XML; other `s:par` values such as `DynamicPlaceholderId` are preserved), then write the printed XML back to the SAME field with `update_fields_on_item(itemId, {"<field name>": "<xml>"})` (or `update_content`). Re-read: `get_components_on_page` shows the variant (`FieldNames`) and every other component is still there. If anything else changed or disappeared, restore the backup immediately.
3. **Authoring GraphQL (`updateItem`).** `node harness/scripts/layout-variant.mjs apply --item <page or partial design id> --uid <rendering uid> --variant <variant definition id>` (add `--dry-run` first). Needs `SITECORE_CM_HOST` and the automation client in `harness/.env.local`; it backs up the original field value and uses the Authoring and Management API (`https://<CM host>/sitecore/api/authoring/graphql/v1/`, mutation `updateItem`). If `SITECORE_CM_HOST` is empty, find the CM host from the Sites/Environment API or the editing host config; if you cannot, record that in manual-tasks.
**Bulk rule (switching or setting a variant on many pages, e.g. every title-only stub).** Do it as a LOOP OF ROUTE 2, through the MCP, in the foreground: per page `get_content_item_by_id` → `layout-variant.mjs patch` → `update_fields_on_item` → read back with `get_components_on_page`, staying under the rate limit (50 requests per 10 s, so pause between pages). Route 3 (`apply`) is NEVER the first choice and NEVER a bulk job: it needs the CM host and is only for when route 2 failed on that item, with the route 2 error quoted. A missing `SITECORE_CM_HOST` is not a reason to leave pages unswitched: the MCP route does not need it. Every page ends with its read-back; a page without one is not done.
4. Only if 1–3 all failed: `variant-checklist.md` + `manual-tasks.md` with the exact component, page/partial, variant, and the errors from each route. Never skip routes 1–3 because of an older "not supported" note.
After the first success, write the route that worked (tool, field, exact call shape, gotchas) into `harness/reference/marketer-mcp-tools.md` → "Verified methods" so the next demo starts there. Apply the SAME route to every non-Default section on every page (`demo-build-pages` step 5), not just the header.

## 4. Do not over-trust a success message
`add_component_on_page`, `update_fields_on_item` and `set_component_datasource` can report success while writing nothing useful (wrong placeholder key, silent field writes, datasource ignored). Every step above ends with a read-back; the read-back, not the success message, decides.

## 5. Placing, ordering, moving and removing components (Marketer MCP, since 2026-10-12)
- Place: `add_component_on_page(..., insertAfterComponentId=<previous> | insertBeforeComponentId=<next>)` (mutually exclusive). Use it to keep plan order.
- Fix a wrongly placed component (wrong placeholder key, wrong order): `move_component_on_page` to the right placeholder/neighbour, or `remove_component_on_page` and add it again. Do not leave an orphaned component and do not list it as manual work.
- Both move and remove ask for confirmation and do one mutation per call without retry; read the live schema for the confirmation argument and re-read with `get_components_on_page` afterwards.
- Before deleting a datasource or any shared item: `get_content_references(itemId)`; only delete items this harness created for this prospect.

## 6. `add_component_on_page` makes a page-local datasource; do not fill it, do not keep it
`add_component_on_page` creates a local item `<page>/Data/<componentItemName>` for the new instance, and if you pass `fields` it fills THAT item. Demo content must live in the site's `Data` instead (demo-build-pages step 4). So: (a) never pass `fields` to `add_component_on_page`; (b) name the instance `harness-tmp-<n>` so leftovers are recognisable; (c) the real datasource is created first under `/sitecore/content/<collection>/<site>/Data/<folder>` and wired with section 2; (d) the auto-created local item is then deleted (`get_content_references` first: it must show no reference after the re-point, then `delete_content`). an earlier demo run ended with ContactForm, Features, FourColumnCta, HeadingCta, Outcomes, ThreeColumnCta, HeroBanner and RichText under `Home/Data`: that is what skipping (a)-(d) produces.

## 7. Display names
Derive the value mechanically from the item name: hyphen → space, first letter of every word upper-case (`contact-us` → `Contact Us`). Routes in order: `create_page` fields, `update_fields_on_item`, `update_content`, then `node harness/scripts/layout-variant.mjs set-field --item <id> --field "__Display name" --value "Contact Us" --language <lang>` (Authoring GraphQL; verifies by read-back). All failed: table in `manual-tasks.md`. Use the language the item really has (read it), not an assumed `en`.

`__Display name` is a versioned, per-language field: write it in the page's language (`en`) on the page's language version, and read it back with `get_content_item_by_id(id, language="en")`. A page whose tree label is still the item name (`about-us`) did not get it.
