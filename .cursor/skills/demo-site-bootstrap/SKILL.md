# Bootstrap a freshly created site so the shared components work in it

A site made from a site template has the standard presentation scaffolding but none of the project-specific items that ProsperaFinancial-style sites carry. The shared definitions (templates, renderings, rendering parameters under the project layer, `renderingsRoot` in `docs/ai/config/project.yaml`) already exist and are REUSED. This skill creates only what lives INSIDE the new site. Use the Marketer MCP; how to do nested placeholders, datasources and variants is in `.cursor/skills/sitecore-reference/references/placeholders-and-variants.md` (earlier notes in `agent-api-limitations.md` are history, not rules).

## Rules
- Run `node harness/scripts/bootstrap-plan.mjs <customer>` first; it lists exactly what is needed (`bootstrap-plan.md/json`).
- Before every write: `node harness/scripts/guard-customer.mjs sitecore-path <customer> "<path>"`.
- Use ids from the manifest ONLY for shared things (templates, folder templates, renderings, rendering parameters). Site-level ids in the manifest (any other site's `/sitecore/content/...` paths, variant definition ids, example items) belong to another site: never use or write them.
- Record every id you create or find in `industry-verticals/<customer>/docs/ai/demos/<customer>/site-manifest.json`; all later phases read site-level ids from there.
- Do not claim a write worked until you re-read it (several fields are silent-writes; see `sitecore-marketer-mcp-reference.md`).

## Step 0 — Probe (read-only)
With `get_content_item_by_path`, list and record in `site-probe.json`: `/sitecore/content/<coll>/<site>` children; `Home`; `Data`; `Presentation/{Available Renderings, Headless Variants, Partial Designs, Page Designs, Styles}`; `Settings`. Also confirm the shared layer exists (`renderingsRoot`, `projectTemplatesRoot` from `docs/ai/config/project.yaml`). If the shared layer is missing in this environment or collection, STOP and tell the SE: the components are not registered there and that is a separate (new-component) job.
If the probe shows there is no `Home` page (some site templates, e.g. Empty, may not create one), STOP and report what the probe found: do not guess a page template. The SE decides how to create Home once, then re-run.
The probe decides each step below: create only what is absent.

## Step 1 — Data root and datasource folders
All page-section datasource content of the demo lives under this site's `Data` root (`/sitecore/content/<collection>/<site>/Data/<component folder>`), never in page-local `<page>/Data` folders; only the Header/Footer partial designs keep their own `Data` child (step 5). Record each folder id in `site-manifest.json` → `dataFolders`.
If `Data` is missing, create it (use the folder template the probe shows other Data roots use; if none, use the template the plan's `folderTemplateId` implies or the Data folder template of the reference site, note the assumption in `manual-tasks.md`, and continue). For each component with a datasource in `bootstrap-plan.json`: create `Data/<datasourceFolderName>` with `create_content_item`, template = `folderTemplateId`. Skip existing. The rendering's datasource location query looks under `$site/Data` for that folder template, so the template and the folder name must match the plan exactly.

## Step 2 — Headless Variants
For each component: ensure `Presentation/Headless Variants/<container>` exists (template **Headless Variants**), then one **Variant Definition** per variant needed (always `Default`, plus every non-Default variant the plan uses and `WithLogoImage` for `Header`), names exactly as the TSX exports (`industry-verticals/prospera/.cursor/skills/sitecore-add-variants/SKILL.md`). Record the variant ids in `site-manifest.json` (they feed the variant checklist).

## Step 3 — Available Renderings
Open `Presentation/Available Renderings/Page Content` (or the probe's equivalent). Its field cannot always be read through MCP. If you can read it: write the existing value + the plan's ids (concatenate, never replace). If you cannot read it, do NOT write: save the pipe-separated list from `bootstrap-plan.md` to `available-renderings.txt`, add "paste this list after the existing value of Available Renderings/Page Content" to `manual-tasks.md`, and CONTINUE: try `add_component_on_page` anyway (the API usually does not enforce Available Renderings). Do not ask or wait.

## Step 4 — Derived page templates
Never point new pages at another site's templates directly. For each distinct page type in `demo-plan.yaml` (`page`, `article`, `landing`):
1. Base = the shared template from `industry-verticals/prospera/docs/ai/catalog/page-template-registry.yaml` (e.g. `/sitecore/templates/Project/Financial/Pages/Article Page`). Read-only.
2. Ensure the folder `/sitecore/templates/Project/<collection>/Pages` exists (Template Folder; create parents if absent; guard-check the path first).
3. Create the template there: `create_content_item` with the **Template** template (`{AB86861A-6030-46C5-B394-E8F99E8B87DB}`), name = the base template's name (`Article Page`, `Page`, ...). Set its **Base template** field (`__Base template`) to the base template id, then re-read to confirm. No own fields are needed; it inherits fields, standard values and insert options from the base.
4. Record `{pageType: derivedTemplateId}` in `site-manifest.json` → `pageTemplates`. `demo-build-pages` uses these ids, never the base ids.
If the write is refused, record the response in `harness/reference/marketer-mcp-tools.md` (limits), fall back to using the base template, and list it in the manual tasks.

## Step 5 — Header and footer partial designs, Page Designs
A partial design is an item in `Presentation/Partial Designs` that carries components, a page design is an item in `Presentation/Page Designs` that lists partials and is mapped to page templates. All are created by API; do not give up on them without trying.
1. **Learn the pattern (read-only)** from the site's own `Partial Designs` / `Page Designs` (the site template may already include some) or, if empty, from the reference site in `sitecore-manifest.yaml`: the template id of a partial design and of a page design, the field names (partial designs list, template mapping `Template To Design`), the header and footer placeholder paths (`get_components_on_page(pageId=<reference partial id>)`), and the encoding of the mapping value. Never write to the reference.
2. Create `Header` and `Footer` partial designs (same template as the reference). Then fill them. Rendering ids: the manifest, otherwise look the rendering up by name under `renderingsRoot`. Placeholder names come from the code (`industry-verticals/prospera/src/components/navigation/*.tsx`). Nested placeholders are DYNAMIC and are DERIVED, never hardcoded: follow `.cursor/skills/sitecore-reference/references/placeholders-and-variants.md` section 1 (key = `<host placeholder path>/<child name>-0-<host DynamicPlaceholderId>`, e.g. `/headless-header/eyebrow-left-0-1`; the numbers come from the host instance you just added and change per page/partial). Add the host, read back its `DynamicPlaceholderId`, build the key, check it with `get_allowed_comps_by_ph`, add the child, re-read and confirm the child sits under that exact key. Every set of renderings in this step ends with that read-back.
   **Header partial design** — exactly this composition, in this order:
   | # | Component | Placeholder | Notes |
   |---|---|---|---|
   | 1 | `Eyebrow` | `headless-header` | MUST be first, i.e. above the Header component. No data source. Variant `WithLinks` when the plan has eyebrow links (step 5b), else `Default`. |
   | 2 | `ThemeSwitcher` | Eyebrow's left placeholder: `/headless-header/eyebrow-left-0-<Eyebrow DynamicPlaceholderId>` (derived) | no data source |
   | 2b | `Navigation` (only with the `WithLinks` variant) | Eyebrow's links placeholder: `/headless-header/eyebrow-links-0-<Eyebrow DynamicPlaceholderId>` (derived; name from the variant's code, step 5b) | data source = Home; Navigation Filter = `Eyebrow Navigation` (step 5b) |
   | 3 | `LanguageSwitcher` | Eyebrow's right placeholder: `/headless-header/eyebrow-right-0-<Eyebrow DynamicPlaceholderId>` (derived) | no data source |
   | 4 | `Header` | `headless-header`, after the Eyebrow (`insertAfterComponentId`) | variant **`WithLogoImage`** (REQUIRED, see below); **data source = the Header data item below (REQUIRED, otherwise no logo renders)** |
   | 5 | `Navigation` | Header's right placeholder: `/headless-header/header-right-0-<Header DynamicPlaceholderId>` (derived) | data source = the site's Home item (or whatever the reference partial uses); Navigation Filter = `Main Navigation` (step 5b), so it lists ONLY the main-menu pages |
   Note: with the `WithLogoImage` variant the Header renders the logo itself and only has `header-right`; the `Default` variant would use `header-left` instead.
   **Header data source (local data of the partial) — do these in this order:**
   1. **Logo to Content Hub FIRST.** Download the logo (`logo` entry of `download-images.mjs`/scraper; if none was found, take it from the screenshot/site `<img>`/favicon fallbacks and note it in `manual-tasks.md`, do not ask). Upload it: `node harness/scripts/content-hub-upload.mjs <customer> --file <logo file> --name logo --alt "<Customer> logo"`. The last output line `RESULT {...}` contains `imageFieldXml` (the Image field value with the Content Hub PUBLIC LINK). If `CH_ENABLED` is not `true` or the upload fails, use the logo's source URL/media item for now, add the logo to `images-to-upload.md` and `manual-tasks.md`, and continue.
   2. **Header component template (own copy for the collection):** create `/sitecore/templates/Project/<collection>/Components/Header` as a derived template (Template folder `Components` first if missing; Base template = `{0DA7AA52-0C24-4721-9B6C-F6D8D9FAAAA0}`, i.e. `/sitecore/templates/Project/Financial/Components/Header`, so it inherits the `LogoImage` field). Re-read to confirm. Record the id in `site-manifest.json` → `componentTemplates.Header`.
   3. Under the Header partial design create `Data` (same template the reference partials' `Data` child uses; probe it), and under it an item named `Header` based on the template from 2. Set `LogoImage` to the `imageFieldXml` from 1 (verbatim). Re-read the item: `LogoImage` is non-empty.
   4. **Datasource — mandatory.** `set_component_datasource(pageId=<Header partial design id>, componentId=<the Header component's id on it>, datasourceId=<that Header data item id>)`, then `get_components_on_page(<partial id>)` must show this item as the Header's datasource. If the tool refuses the partial design id, use the next route from `placeholders-and-variants.md` section 2. A Header without its datasource is a FAILED step.
   **Header variant — mandatory.** Ensure the site's `Presentation/Headless Variants/Header` container has `Default` AND `WithLogoImage` (step 2 of this skill; ids in `site-manifest.json`). Then set `WithLogoImage` on the Header component with the method ladder in `placeholders-and-variants.md` section 3 (tool argument → layout XML via MCP + `harness/scripts/layout-variant.mjs patch` → Authoring GraphQL `layout-variant.mjs apply`) and confirm with `get_components_on_page` that the Header shows the variant (`FieldNames` = the WithLogoImage id). Without it the logo does not render. Do this AFTER the Navigation child is added (the layout XML is then complete) or, if you patch earlier, re-read afterwards and confirm nothing was lost. Do not accept "the MCP cannot set variants" as an answer: the ladder has three routes; only when all three fail put it in `manual-tasks.md` (marked required) with the three errors. Record the route that worked in `harness/reference/marketer-mcp-tools.md` → "Verified methods".
   **Footer partial design:** `SiteFooter` (rendering name in the manifest; data source = a footer item you create under the partial's `Data`, fields filled from the content plan).
   Rejected because the item is not a page? Try the variant the tool schema allows (see `harness/reference/marketer-mcp-tools.md`), once, then the layout-XML route in `placeholders-and-variants.md`. If one component still fails, continue with the others, record the exact error in `harness/reference/marketer-mcp-tools.md` → "Verified methods", and add ONE manual task naming only what is missing (component, placeholder, data source, variant).
3. Create Page Designs `Page` and `Article` (page design template from step 1) listing the `Header` and `Footer` partials (plus any body partial the reference uses), then set the **Template To Design** mapping on the Page Designs folder: derived `Page`/`Landing` templates → `Page` design, derived `Article` template → `Article` design. Append to an existing mapping value, never replace it. Re-read to confirm.
4. Verify later (demo-build-pages step 2): the first sub-page renders header and footer. A partial-design failure never blocks the build; the SE adds the two components by hand and the rest continues.

## Step 5b — Main menu vs eyebrow links: Navigation Filters and the Eyebrow variant
The prospect's header has TWO link groups and they must not be mixed: the **main menu** (e.g. Critical Power, Motive Power, Dedicated Maintenance, Resources, Success Stories, Login) rendered by the Header's Navigation, and the small **eyebrow bar** above it (e.g. About us, Join our team, Locations, Contact us) rendered by the Eyebrow. `nav.json` has them apart (`items` vs `eyebrow`; `eyebrowExtras` = phone number / CTA button, which are not pages). The plan gives every page a `navGroup` (`main` | `eyebrow` | `none`). Without this step the Navigation lists every page under Home, eyebrow links and sub-pages included.
1. **Find the filters (derived, never hardcoded).** Pages have a `NavigationFilter` field ("Check to hide in navigation filters": Breadcrumb / Footer / Main / Sidebar / Sitemap Navigation). Read the field's definition on the derived page template (find the field item under the template, e.g. `get_content_item_by_path`; its `Source` says where the options live), then list that folder for the NEW site and record each option's item id in `site-manifest.json` → `navigationFilters` (`{ "Main Navigation": "{id}", ... }`). Never use another site's filter ids.
2. **Eyebrow Navigation filter.** If the plan has `navGroup: eyebrow` pages, create one more filter item `Eyebrow Navigation` in that same folder, same template as the existing options, and record its id.
3. **Page rule (applied while pages are built, `demo-build-pages` step 3).** `NavigationFilter` is a "hide in" list, written as the ids joined with `|`: `main` pages hide in `Eyebrow Navigation`; `eyebrow` pages hide in `Main Navigation`; `none` pages (story pages, dropdown children, anything else) hide in BOTH. Home is not a menu entry. Read back one page to confirm the stored value.
4. **Navigation components pick their filter.** Read the Navigation rendering's parameters (`get_component(<Navigation rendering id>)` → its Parameters Template; look for the field that holds the navigation filter, e.g. `NavigationFilter`/"Navigation Filter") and set it per instance with the layout-XML route of `placeholders-and-variants.md` section 3 (`layout-variant.mjs patch --uid <navigation uid> --param <ParameterName>=<filter id>`): header Navigation = `Main Navigation`, eyebrow Navigation = `Eyebrow Navigation`. If no such parameter exists, say so in `manual-tasks.md` and in `harness/reference/marketer-mcp-tools.md` → "Verified methods"; do not drop the page-level `NavigationFilter` values.
5. **Eyebrow variant `WithLinks` (only when there are eyebrow links).** The shared Eyebrow only has `eyebrow-left` and `eyebrow-right` placeholders plus the search button, so links need a NEW VARIANT. Code, in the customer's own app copy only (`industry-verticals/<customer>/src/components/navigation/Eyebrow.tsx`; never Prospera): add `export const WithLinks = ...`, a copy of `Default` with one more `<AppPlaceholder name="eyebrow-links" .../>` between the left placeholder and the right group (keep the search button). Sitecore: add Variant Definition `WithLinks` to `Presentation/Headless Variants/Eyebrow` (name = the export name), set it on the Eyebrow with the variant ladder, add a `Navigation` component into the derived key `/headless-header/eyebrow-links-0-<Eyebrow DynamicPlaceholderId>` (section 1 of `placeholders-and-variants.md`; the name `eyebrow-links` comes from the code you just wrote), datasource = Home, filter = `Eyebrow Navigation`. Phone number and CTA button from `eyebrowExtras`: not pages; if the shared components cannot show them, add one line to `manual-tasks.md`.
6. If there are no eyebrow links, the Eyebrow stays `Default` and only steps 1 and 3 (main vs none) apply.

## Step 6 — Verify and hand on
Re-read every created item (`get_content_item_by_path`), compare with the plan, list gaps. Header check (from `get_components_on_page` on the partial, not from memory): Eyebrow above Header; ThemeSwitcher and LanguageSwitcher stored under `/headless-header/eyebrow-left-0-<id>` / `eyebrow-right-0-<id>` of the Eyebrow's real `DynamicPlaceholderId`; Navigation under `header-right-0-<id>` of the Header's real id; Header datasource = the `Data/Header` item with `LogoImage` filled with a Content Hub public link; Header variant = `WithLogoImage`; Eyebrow variant `WithLinks` (when planned) with its own Navigation in the derived `eyebrow-links-0-<id>` key; header Navigation filter = Main Navigation, eyebrow Navigation filter = Eyebrow Navigation. Then render the first sub-page (`get_page_screenshot`) and check the logo, switchers and navigation are visible. Write `site-manifest.json`: `{ siteRoot, dataRoot, dataFolders: {Component: id}, variants: {Component: {Variant: id}}, availableRenderingsItem, pageTemplates: {pageType: id}, partialDesigns: {Header, Footer}, pageDesigns: {Page, Article}, home }`. Run the guard `check`. Then continue with content (Phase 3) and `sitecore-build-pages`.
If any step fails twice, stop and report what exists, what is missing, and which manual step unblocks it.
